# QuickTicket

A Bookmyshow-style  project. It demonstrates small Go services, Redis seat holds and distributed locks, a virtual waiting room, PostgreSQL booking transactions, Kafka events, transactional outbox delivery, and mock payments.

## Independent service builds

Each Go microservice is an independent Go module with its own `go.mod`, `go.sum`, and multi-stage `Dockerfile`:

- `services/catalog/`
- `services/inventory/`
- `services/booking/`
- `services/waiting-room/` (HTTP handlers, queue service, admission-token service)
- `services/booking-events/`
- `services/search/` (Elasticsearch query API and Debezium CDC indexer)

Docker Compose builds each service separately using that directory as its build context. The Dockerfile downloads dependencies, builds a static Go binary, and copies only the binary into a minimal runtime image.

To build all service images without starting containers:

```bash
docker compose build
```

To build one service:

```bash
docker compose build catalog
docker compose build inventory
docker compose build booking
docker compose build waiting-room
docker compose build booking-events
docker compose build search
```

To run the stack:

```bash
docker compose up
```

## Architecture

| Service | Base URL | Responsibility |
|---|---|---|
| Catalog | `http://localhost:8081` | Users, venues, performers, events |
| Inventory | `http://localhost:8082` | Ticket CRUD, temporary seat holds |
| Booking | `http://localhost:8083` | Bookings and mock payment |
| Waiting Room | `http://localhost:8084` | FIFO queue and admission tokens |
| Booking Events | background worker | Consumes Kafka booking events |
| Search | `http://localhost:8085` | Event discovery API backed by Elasticsearch; index populated from PostgreSQL CDC |

Infrastructure: PostgreSQL (5432, logical WAL enabled), Redis (6379), Kafka (9092), Debezium Connect (host port 8086, container port 8083), Elasticsearch (9200).

## 1. Start the project

Requirements: Docker and Docker Compose.

```bash
docker compose up --build
```

The first startup creates the PostgreSQL schema from `db/schema.sql`. Check service health:

```bash
curl http://localhost:8081/health
curl http://localhost:8082/health
curl http://localhost:8083/health
curl http://localhost:8084/health
curl http://localhost:8085/health
```

Expected response:

```json
{"status":"ok"}
```

Follow logs:

```bash
docker compose logs -f catalog inventory waiting-room booking booking-events search debezium
```

> **Existing Docker volume:** the schema file is only applied automatically when PostgreSQL initializes an empty data volume. If you already ran an older version, apply the migration in `db/migrations/002_allow_ticket_rebooking.sql` manually (see Database migration below). To reset all local data instead, run `docker compose down -v` and then `docker compose up --build`.

## 2. API conventions

- All request and response bodies are JSON.
- IDs in examples are generated by PostgreSQL. Use the IDs returned by your own create requests.
- CRUD update uses `PUT` with only the fields you want to change.
- There is no authentication in this learning project. The `user_id` is supplied in request bodies.
- The commands below assume the services are running on localhost.

## 3. Create the catalog data

Create a user:

```bash
curl -i -X POST http://localhost:8081/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"Alex Morgan","email":"alex@example.com"}'
```

Example response (`201 Created`):

```json
{"id":1}
```

Create a venue:

```bash
curl -i -X POST http://localhost:8081/venues \
  -H 'Content-Type: application/json' \
  -d '{"name":"City Arena","city":"Berlin","capacity":5000}'
```

Create a performer:

```bash
curl -i -X POST http://localhost:8081/performers \
  -H 'Content-Type: application/json' \
  -d '{"name":"The Example Band","description":"Live music"}'
```

Create an event. Replace `venue_id` and `performer_id` with the IDs returned above. Use an RFC3339 timestamp:

```bash
curl -i -X POST http://localhost:8081/events \
  -H 'Content-Type: application/json' \
  -d '{"name":"Berlin Live","description":"Evening concert","event_type":"concert","starts_at":"2027-06-15T19:30:00Z","venue_id":1,"performer_id":1}'
```

### Catalog CRUD endpoints

The same CRUD pattern is available for each resource:

| Operation | Method | Path |
|---|---|---|
| List | GET | `/{resource}` |
| Create | POST | `/{resource}` |
| Read one | GET | `/{resource}/{id}` |
| Update | PUT | `/{resource}/{id}` |
| Delete | DELETE | `/{resource}/{id}` |

Supported resources: `users`, `venues`, `performers`, `events`.

Examples:

```bash
curl http://localhost:8081/events
curl http://localhost:8081/events/1
curl -X PUT http://localhost:8081/venues/1 \
  -H 'Content-Type: application/json' \
  -d '{"capacity":6000}'
curl -i -X DELETE http://localhost:8081/performers/1
```

Required fields when creating:
- User: `name`, `email`
- Venue: `name`, `city`, `capacity`
- Performer: `name`; `description` is optional
- Event: `name`, `event_type`, `starts_at`, `venue_id`, `performer_id`; `description` is optional

| Operation | Method | Path |
|---|---|---|

| Update | PUT | `/tickets/{id}` |

## 5. Join the virtual waiting room

Join the queue for an event:

```bash
curl -i -X POST http://localhost:8084/queue/join \
  -H 'Content-Type: application/json' \
  -d '{"event_id":1,"user_id":1}'
```

If admitted, the response contains an `admission_token`:

```json
{
  "event_id": 1,
  "user_id": 1,
  "status": "admitted",
  "admission_token": "COPY_THIS_TOKEN",
  "admission_expires_in_seconds": 600
}
```

If the user is still waiting, the response looks like:

```json
{"event_id":1,"user_id":2,"status":"waiting","position":1}
```

Check the queue position/admission status:

```bash
curl -i -X POST http://localhost:8084/queue/status \
  -H 'Content-Type: application/json' \
  -d '{"event_id":1,"user_id":1}'
```

Keep the returned token. It is required by both the hold and booking APIs. The default concurrent admission capacity is 2 and token TTL is 600 seconds. Configure these in `docker-compose.yml` using `QUEUE_CAPACITY` and `ADMISSION_TTL_SECONDS`.

## 6. Hold a seat (Inventory)

Use the ticket ID, user ID, and the admission token returned by the waiting-room service:

```bash
curl -i -X POST http://localhost:8082/holds \
  -H 'Content-Type: application/json' \
  -d '{"ticket_id":1,"user_id":1,"admission_token":"COPY_THIS_TOKEN"}'
```

Successful response (`201 Created`):

```json
{"ticket_id":1,"user_id":1,"expires_in_seconds":300}
```

A hold expires after five minutes. To release your own hold before it expires:

```bash
curl -i -X DELETE http://localhost:8082/holds \
  -H 'Content-Type: application/json' \
  -d '{"ticket_id":1,"user_id":1}'
```

## 7. Create a booking and test mock payment

Successful payment:

```bash
curl -i -X POST http://localhost:8083/bookings \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"ticket_ids":[1],"admission_token":"COPY_THIS_TOKEN","mock_payment_result":"success"}'
```

The response includes the booking ID, total, booking status, and payment status:

```json
{
  "booking_id": 1,
  "user_id": 1,
  "ticket_ids": [1],
  "total": 75,
  "status": "confirmed",
  "payment_status": "succeeded"
}
```

Simulate a declined payment using a different available ticket and a valid hold:

```json
{
  "user_id": 1,
  "ticket_ids": [2],
  "admission_token": "VALID_ADMISSION_TOKEN",
  "mock_payment_result": "failure"
}
```

Send that JSON to `POST http://localhost:8083/bookings`. The booking is recorded as cancelled, payment status is failed, and the ticket is returned to available inventory.

List bookings:

```bash
curl http://localhost:8083/bookings
```

## 10. Automated end-to-end test (Python)

The standard-library test script creates its own user, venue, performer, event, and tickets. It then exercises:

- Health checks for all four HTTP services.
- Waiting-room admission and token issuance for two users.
- Exclusive ticket holds (the second buyer must receive HTTP 409).
- Successful booking (ticket becomes `booked`).
- Failed mock payment (booking is cancelled and ticket returns to `available`).
- Booking history and, by default, published transactional-outbox rows.

Start the stack and apply migrations first:

```bash
docker compose up --build -d
docker compose exec -T postgres psql -U quickticket -d quickticket < db/migrations/002_allow_ticket_rebooking.sql
docker compose exec -T postgres psql -U quickticket -d quickticket < db/migrations/003_transactional_outbox.sql
```

Run from the repository root with Python 3.10+:

```bash
python3 tests/e2e_quickticket.py
```

The outbox assertion uses `docker compose exec` and `psql`, so Docker Compose and the PostgreSQL container must be available to the machine running the script. To skip only that database-level assertion:

```bash
python3 tests/e2e_quickticket.py --skip-outbox-check
```

The test creates uniquely named records and does not delete them, making failures easier to inspect. It expects the default waiting-room capacity of at least two. It does not reset your database or Redis data.

## 11. What to observe while testing

- **Redis:** temporary `ticket:hold:{ticketID}` keys, per-seat `ticket:lock:{ticketID}` keys, and event queue/admission sorted sets.
- **Waiting room:** submit multiple users for the same event; only up to `QUEUE_CAPACITY` are admitted at once. Poll status for users still waiting.
- **Double booking:** try to hold the same ticket with two users. The second request should receive a conflict while the hold is active.
- **PostgreSQL:** ticket status, booking status, payment status, and booking-ticket relationship.
- **Kafka:** after a booking, inspect `docker compose logs -f booking-events` for the consumed booking event.

## 11. Database migrations for existing volumes

If you already initialized PostgreSQL with the earlier schema, run this once:

```bash
docker compose exec -T postgres psql -U quickticket -d quickticket < db/migrations/002_allow_ticket_rebooking.sql
```

This removes the old unique constraint on `booking_tickets.ticket_id`. It is needed because a failed payment keeps its cancelled booking record while making the ticket available for another booking.

Apply the transactional outbox migration:

```bash
docker compose exec -T postgres psql -U quickticket -d quickticket < db/migrations/003_transactional_outbox.sql
```

New databases get the outbox table automatically from `db/schema.sql`.

## Search and CDC

Search is a separate read-only service. PostgreSQL remains the source of truth; Debezium reads event-table changes from PostgreSQL logical WAL and publishes them to Kafka topic `quickticket.public.events`. The Go Search consumer indexes event documents in Elasticsearch using the event ID as the document ID. The initial Debezium snapshot populates existing events; subsequent inserts, updates, and deletes maintain the index. See [Search CDC design and API](docs/SEARCH_CDC.md).

For existing Docker volumes, the PostgreSQL container is configured to start with `wal_level=logical`; restart the PostgreSQL container after updating Compose so the setting takes effect. Connector registration is automatic on Compose startup. This is a local development setup without Elasticsearch authentication or production-grade Kafka Connect replication.

## Scope and known limitations

No frontend, real payment gateway, authentication, API gateway, Python service, Kubernetes, or production-grade deployment. The project is intentionally focused on CRUD, seat contention, temporary holds, admission control, transaction boundaries, and asynchronous events.

Booking rows and `BookingCreated` outbox events are inserted in the same PostgreSQL transaction. The booking service polls pending outbox rows and publishes them to Kafka, marking them published after acknowledgement. Delivery is at-least-once: consumers should deduplicate by the stable `event_id` because a crash after Kafka acknowledgement but before the database update can cause a repeat. Apply migration `003_transactional_outbox.sql` to existing databases. Redis locks are short-lived coordination leases; PostgreSQL conditional updates and transactions remain the final inventory consistency guard.
